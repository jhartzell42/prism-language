# Prism: chapter summaries

## 1. A language whose only subject is time

The chapter opens on an afternoon every reader has lived: a "show archived" checkbox that unticks itself one time in five, because a setter notified its observers one line before it wrote its field, and a re-render read the model back half-updated. The thesis follows from that bug. The many bugs of interactive programs are one bug, a value whose set of writers is not a fact about its type. Functional reactive programming makes the writers a fact with two types, a value that happens and a value that holds, tied by one law: a held value changes only through the events named in its definition, and only when the moment ends. Prism is a language that keeps that law and no other, and the list of what it refuses is the evidence.

The chapter first names the four faces of the bug (uncontrolled mutation, action at a distance, "who can change this?", order within a moment) and shows one cause under all four. It then asks for a bigger version of `const`: a policy on who may write and when. A policy removes sentences from a language, and a library can only remove what its host lets it name, so the policy has to be a language. Each paradigm gets a picture, the constraint it adds, and the place its own documentation shows the problem returning: callbacks, objects and the Observer pattern's "make sure Subject is self-consistent", React's tearing and Suspense, signals as the behavior half of FRP found independently, Rx as the event half without behaviors as a law, Elm as the friendly proof that a language-level mutation policy works, Haskell's `dFoo`/`eFoo` naming and open door to `IO`, and the synchronous languages as allies built for fixed structure.

The goals come next, each stated as a promise that some version of the afternoon cannot happen. The refusals section turns the list of missing features into the definition of the language: no sampling, no prompt switching, no assignment, no events from nothing, no effects or callbacks, no node values, no request on creation, no placeholders, no custom monads, no reaching into another widget, no exceptions as control flow, no ambient context, no threads or phases, no clock, no dynamic fields in elements, no introspection. Each entry puts the bug first and then the mechanism the implementation no longer needs, such as a scheduler, a collector, a lock or a retry loop.

The chapter then draws the boundary. The language has no effects; the World has all of them, owns the loop, and opens every occurrence. Only plain data crosses: elements going out, responses by path and state by element value coming in. The creation rule appears here in full, stated prominently. Two programs close the chapter: the counter from the afternoon, with every declaration it uses, and a file viewer whose contents are a state element valued in its first occurrence, with an `Unavailable` arm the compiler insists on and a Quit button that fires a `Process.Exit` request. Each of the afternoon's questions gets a one-line answer.

A section then argues that Prism is a pure functional language, by two tests rather than by the description-versus-performance line alone: substitution (a definition in place of its name is the same program) and Sabry's strategy independence (any propagation order that respects dependencies gives the same answers). It takes the parts that look impure in turn: holds are definitions whose history is readable only through the one-step delay; a hold inside a `rebuild` starts on a clock the inputs choose, so a blueprint denotes a behaviour from its build occurrence on; widgets are the one non-referentially-transparent thing in reach and the language refuses to hold them, holding blueprints as Haskell holds `IO a`; requests are the things whose answers arrive in a later occurrence, which is what separates them from function calls; and the language is pure but not total, an aborted occurrence being bottom in the fold. It claims Prism is purer than Haskell in one specific respect: there is no IO type to lift.

The introduction leaves the definitions themselves to later chapters and only claims that the refusals are enough. It hands off to the worked examples, where every rule the book defines is first seen doing work, occurrence by occurrence, before it is defined.

## 2. Worked examples

The chapter opens with the claim that the programs are the language and the walkthroughs are the laws applied to them. It offers fourteen programs, from a counter to a shell that hosts other programs, each followed by an occurrence-by-occurrence account of what the World sends, what fires in dependency order, what commits, and what the element list looks like afterwards. A reader who has read the specification can predict each walkthrough and check; a reader coming cold meets every later rule here first.

The conventions fix the vocabulary for the book: occurrences numbered from zero with zero as the build, inputs addressed by path and simultaneous, the only promised order being dependency order, and a small shared set of declarations under `Gui`, `Ui`, `Fs`, `Time` and `Process`, each declared before first use. The first programs build up the core: the counter, a text input with a cursor, a todo list driven by `for` over a keyed map, a button that relabels itself (a dynamic field lifted into `rebuild` with a fresh slot per change), a file viewer over a state element, and a stopwatch reading `Clock` as state.

The middle programs introduce interception. A sandbox confines file paths under a root and denies everything else through `Defer`, answering in a later occurrence. A vertical box lays out children and hit-tests pointer input in Prism. A cache answers hits itself and forwards misses. A chat client holds a socket and folds messages into a model. Each walkthrough points at the moment where a rule decides the outcome: a click in the occurrence of a rebuild goes to the old slot, a widget built mid-occurrence sees the whole occurrence, a request is answered later or not at all.

The last programs reach past the GUI. A line counter runs under the CLI World with standard input as a response stream. A tiny HTTP server keys connections in a map. A test script for the counter shows the conformance suite's steps against the Test World. A shell hosts other programs as interceptors, multiplexing their elements onto one outer World, so that each layer can be inserted or removed without its children knowing, and routing against the opened list means no layer can send an input to something the user has not seen.

The closing section states what the fourteen share: equations over three kinds of name, built once, driven by plain data to known paths, with no callbacks, no "right now" reads, no effects except fired requests, and no half-new moment except through the tag law. The chapter does not define any rule formally; it leaves that to the following chapters, each of which points back to the occurrence where its sentence did its work, starting with the language core.

## 3. The language: sigils, lexical structure, values and types, expressions

The chapter opens on `total = price * quantity`, a line where you cannot tell without scrolling whether it ran once or on every keystroke, and on the Reflex habit of naming variables `dPrice` and `eQuantity` against the library author's advice. The thesis: a Prism program is a set of equations between things that are true, things that happen and things that exist, and the sigils on the names say which before a type checker runs. The chapter covers the part of the language that holds still, written so two parsers built from the text agree on every program.

Sigils come first. `!` is an event, `$` a dynamic, `@` a widget, `?` an optional, and bare is plain; they stack leftmost outermost, functor values nest inside plain aggregates, and a function's name takes the sigil of what it returns. The section argues against the alternatives: optional sigils would leave the boundary between styled and unstyled code unreadable, and inferred sigils shown by an editor would make review depend on tooling. The lexical section then goes down to the character, because the conformance suite fails the day the Rust and Haskell lexers disagree: comments, identifiers, keywords, literals (integer-spelled literals are `Nat | Int` by inference defaulting to `Int`, decimal-spelled are `Float`, `-1` is an `Int`), operators, the offside rule with `:` as block opener and more-indented lines continuing a statement, and paren-less calls where commas belong to the outermost call on the line.

The values section is boring on purpose so that nothing competes with time. Primitives (`Nat`, `Int` as 64-bit, `Float`, `Bool`, `Char`, `Text`), three built-in traits for equality, ordering and arithmetic resolved by inference, arrays indexed by `Nat` returning `?T`, sorted maps, records, tuples, declared types, optionals, and the extensible variant `Element` that elements belong to. Absence lives in the type and nothing plain can be mutated. Records have equality but no ordering; elements compare by tag and plain fields, excluding the request event.

Expressions finish the chapter: lifting read off operand sigils at every application (all plain stays plain, dynamics give a prompt dynamic, dynamics plus one event give an event with the dynamics read before the occurrence, two events are an error), `?` lifting as an applicative at the plain layer, application and precedence, statements, lambdas with `_` as pronoun and `\|a, b|` for named arguments, `match` and `if` with no guards and no `else`-less `if`, text interpolation, and `for` as an expression over plain collections. A diagnostics section and the layout corpus, the lines both lexers must tokenise identically, follow.

The negative space is explicit: no introspection, no symbol with two meanings (`<=` is only less-or-equal, `then` only hold, `<-` only bind), no guards, no explicit braces, no block comments, no tabs, no `else`-less `if`, and no `read`/`update` blocks or `&` references, which chapter 3 describes at its end. Each removes a second way to write something and a case on which parsers could disagree. The chapter also names the kind of each sigil (event functor, dynamic functor, widget monad, optional) and argues for the offside rule at the top of its Layout section, and its last three sections cover `&` references with `read` and `update` blocks, user-defined traits and modules, and a package system. The chapter hands the meaning of `!` and `$` to the next chapter, where events, dynamics and the occurrence get their laws.

## 4. Events, dynamics, and time

The chapter opens by saying that everything a Prism program does happens in an occurrence, and an occurrence is a transaction with a before, an after and no visible inside. Every interactive program asks three questions over and over: what is true now, what just happened, and what exists. Most languages answer with a variable, a callback and an object that disagree about time; Prism answers with three kinds of value whose sigils name their relation to one clock. The claim is that a small set of laws suffices, and the tag law alone turns a whole class of cyclic programs into legal ones.

Events come first, introduced by the handler that ran at the wrong time. An event is a thing that occurred, not an object with `.preventDefault()`. Simultaneity is defined, not raced: a program never observes two events in order inside an occurrence. `!never` is the identity for merge, and there is no `!always`. Merge is leftmost, with the reasoning for why the left wins. `on` gives an event a dynamic's value from before the occurrence. Lifting over one event fires exactly when that event fires, and `!Filter` is the one way to drop firings. `!Switch` gives a parent one event across every build of a `rebuild`. Events are values and need no subscription or disposal.

Dynamics come next, introduced by the variable read in the middle of an update. A dynamic changes in exactly one way, when its change event fires, and that sentence is the whole mutation policy. The tag law says a dynamic read at an event gives its value before the occurrence. The change law says derived dynamics are prompt and change once per occurrence. Hold, glitch freedom, equality of readings, and the absence of sampling follow, with what refusing sampling buys and how the behavior side stays hidden. The time section then defines the occurrence as a transaction, the dependency graph, prompt and delayed edges (tags, a switch's hold of inner events, a hold's value side), heights, legal cycles through delayed edges, construction mid-occurrence, and determinism.

A "laws as tests" section pins each law with a short program and script: the left wins, the tag reads before, a hold has its initial value in its build occurrence and adopts a firing there, the diamond does not glitch, two readings agree, `!Switch` swallows a block's birth, `$Join` is prompt on both sides, a nested `rebuild` built in the occurrence its dynamic changed builds once with the new value, nothing answers in the occurrence it was asked, and a prompt cycle formed through a widget function is reported rather than run. A practical section closes with folding with hold, gating with `on`, debouncing through a `Time` element, and accumulating a map.

The negative space names four refusals (no sampling, no prompt switching, no events from nothing, no clock) and what they share: each removes a way for the program to see an occurrence from inside. The chapter leaves lifetimes alone. Events and dynamics never need to be born or die, so the next chapter takes up the one thing that does, the widget.

## 5. Widgets and switching

The chapter opens on the subtree that was removed while its listener lived on, and on the component remounted by a parent's render that fetched twice and let an old response overwrite a new one. Both bugs treat something with a lifetime as if it had none. The thesis: a widget is the one thing in Prism with a lifetime, so state, IO, identity, cycles and subscriptions are all owned by one, and three constructs (`rebuild`, `for`, and lifting over `@`) let a program change its own structure while two primitives, `!Switch` and `$Join`, bring results across the boundary.

The first part separates blueprint from widget: a blueprint is the value of type `@a`, a widget is what one bind builds, with identity, a path, holds, placeholders, slots and children, and widgets are never values. Building is the only doing; the World performs everything. The button is the archetype because it has every property at once, and the word stops meaning GUI once a socket is seen to have them too. Widget blocks are where "one way to change anything, written next to the thing" becomes syntax: holds appear only there, bindings are mutually recursive through delayed edges, every binding is marked build-time or occurrence-time, results can be bundles, blueprints can be arguments, `@main` takes nothing (arguments and environment are state elements), and `@started` is a pure `rebuild` over a constant that fires once at build.

`rebuild` gets the longest treatment, opened by the detail pane whose stale subscription wrote an old id into the model. Its result event fires in every build occurrence including the first and goes to the caller. A rebuild resets everything the old node owned; a generation that fails to build does not fire the `rebuild`'s event and is reported. State meant to survive goes outside the `rebuild`, and the cost of a rebuild is what the block builds, so the way to reduce it is to narrow the dynamic. A `rebuild` built mid-occurrence over a dynamic that changed builds once with the new value, and `rebuild` is not a delay. `!Switch` and `$Join` then get their asymmetry argued: a dynamic always has a value to switch to, so the join can be prompt, while an event created during n has no answer to "did it fire at n", so the switch is not.

Lifting over `@` is defined once (binding a dynamic of widgets means a `rebuild`, switched or joined), and `for` follows, opened by deleting item 3 and losing item 4's expanded state. Keys decide which block survives, which paths stay stable, and which hold keeps its state. Consolidation is by result kind and is prompt. Arrays are second class because index keys rebuild every later row on insertion. A patterns section walks master-detail, tabs, a modal dialog, a list with selection and a wizard, each asking what rebuilds when. An invariants section lists each promise with its bound party and enforcer.

The chapter states that no switching construct creates or defers an occurrence, and closes on four widget refusals (widgets are not values, no hooks, no request on creation, no mutation) and the machinery each spares: no collector, no lifecycle scheduler, no effect reconciliation, no dirty tracking. Elements appear throughout but are left undefined; the next chapter defines them and the interceptor.

## 6. Elements and interception

The chapter opens on the component that fetched on mount, fetched again on re-render, and showed a stale avatar after a race the test suite could not reach. The thesis: an element is the only thing a program can say to the outside and the only thing the outside can address in reply. The chapter defines that channel, the rule that nothing it asks for is answered in the occurrence it asked, the two identities of a slot, the element list as an ordinary dynamic, and `intercept`, the primitive that lets a widget stand where the World stands so that toolkits, sandboxes, caches and mocks are Prism code.

Tags declare elements: a name, plain fields, and any subset of `requests`, `responds` and `state`. A dozen declarations across GUI, files, network, time and process show why each part is what it is, and four rules follow from elements being plain data. `@Element` makes a slot and returns what the tag declares. The creation rule is quoted in full and argued: an `Fs.Load` that read on creation would save a line and cost the three things `@started` exists for. Its complement is that state has a value in its creation occurrence, an observation and not a firing. A slot has two identities: a path for conversations (bind positions, `rebuild` generations, `for` keys, never reused) and a value for facts (equal state elements share one dynamic).

The element list is a dynamic `$(Path ==> Slot)`. Routing goes against the list as the occurrence opened, an unknown path aborts the occurrence, and the diode says inputs change the list but list changes never cause inputs. Dynamic fields lift into a fresh slot per change, walked case by case, with a declared-dynamic-field alternative argued against. A long section shows why state must be there in its first occurrence by trying three designs in turn (state as a request, an interceptor hiding the delay, a `NotYet` placeholder) and showing each failing, then defines the oracle and shows that query-plus-subscription and versioned channels fall out of it.

`intercept` follows, opened by the global `fetch` replacement that proxied the wrong widget. Downward, responses go by path and state goes through a supplier, a dynamic of functions from element to a widget returning the state dynamic, built in the interceptor's node once per distinct value. Upward, the interceptor makes elements with `@Element` or nothing reaches out. Forwarding is manual, and a table-driven alternative is argued against. Typing refines per tag inside `match` arms; answering a request takes a `Defer`; denial must be a value of the state type. Invariants are listed with their bound parties. The chapter then builds a GUI library as interceptors on the two World primitives `Gui.Window` and `Gui.Scene`, with `Ui.*` tags, leaves, layout, hit-testing and focus written in Prism.

The recapitulation compresses the chapter and leaves the bottom of the stack undefined: what the loop below the outermost interceptor must do. That is the next chapter, which is short because this one took everything else.

## 7. Worlds

The chapter opens on the context object handed over at startup, stashed in a global, read after teardown, and eventually discovered to be the render loop, the clock and the filesystem at once. The thesis: a program cannot write a byte, read a clock or hand anyone a callback, so something outside must do all of that, and the design of the boundary lies in how little that thing has to know. A World is the outermost interceptor, written in the host language, the owner of the loop and the only starter of occurrences, driving the runtime through one synchronous call per occurrence with plain data both ways.

The run call is given whole. In: responses by path (at most one per path per occurrence), pushes by element value, and an oracle answering state from the snapshot as the occurrence opened. Out: the element list, request firings per slot, the result and errors. The list is a description the World reconciles to, never a trigger. Nothing else crosses, and occurrence zero builds `@main` with the oracle live. The snapshot discipline comes next, opened by the Binance and Kubernetes snapshot-plus-changes procedure: the World keeps the last value supplied for every state element, the oracle cannot fail because unavailability is a case of the state type, and the World stitches native reads and watches before anything reaches the snapshot. A directory listing is traced through the race, and events-only and dynamics-across designs are argued against.

Turns and `Defer` follow. A turn is the occurrences a World runs before acting, and `Defer` is the only way a turn is longer than one. It exists because an interceptor cannot start an occurrence yet must answer requests later. It is bounded without a cap: each `Defer` slot is answered at most once per turn, and firing again is deferring backwards, an error. Named phases (layout, focus, frame) are considered as a hypothetical and left out. An HTTP cache is traced through a turn occurrence by occurrence, answering some requests itself and forwarding the rest.

The obligations of a World are each stated with the party they protect: send only to known paths, discard late results, never answer in the request's occurrence, keep the oracle synchronous and consistent, answer `Unsupported` for unknown request tags, report unknown state tags. The world core writes these once in the host language, with the turn loop, `Defer` bookkeeping, snapshot and pushes, and the chapter treats GUI as one vocabulary spoken by many Worlds rather than a World concept.

The negative space lists what a World cannot do (no scheduler, priorities or budget, no clock inside, among others) and what each spares, then closes with a one-paragraph definition of a World. Three sections appended after it cover hot reload of a widget subtree, persistence of holds, and real time through a tick World and a bounded occurrence. The concepts are now complete; the next chapter puts them under eight real programs to find their hard moments.

## 8. Use cases in depth

The chapter opens on eight hard moments: the file that changes on disk as the user presses undo, the fill that lands with the book update that would have re-quoted it, the emergency stop that arrives with the tick, the member who leaves a room as someone speaks to it, the source that changes as its compile finishes, the window that quits under the click that raised it, the jump pressed on a frame boundary, the time range that changes as the old range's data arrives. The thesis: these programs are not toys, and each one, taken far enough, reaches a moment where two things happen in one instant and the answer is a line of the program.

Each deep dive follows one frame: the element vocabulary, the structure of the program, the hard moment walked occurrence by occurrence, what the goals buy, and where the language is awkward or wrong. The text editor has exactly the states a framework claims to manage (text, cursor, undo, dirty flag, search) and the outside events it does not, and giving each state one defining line decides which write wins. The market-data consumer shows what "act on exactly the state you saw" means and treats latency as an implementation question. The control loop gets a synchronous-language reading and admits where it is wrong.

The chat server derives presence as a dynamic and handles persistence through `Store.*`. The build system treats targets as state over files and shows where a spreadsheet is the same structure until it is not. The shell and window compositor model processes as state keyed by id, spawned by request and killed under the World's cancel-on-teardown obligation, and the compositor multiplexes children's scenes. The game shows replay falling out of the transcript for free. The HTTP dashboard builds polling and caching as interceptors and draws a chart.

The last section names where Prism is the wrong language: batch and throughput work, sequential algorithms, data-parallel pipelines, programs that are one pure function, hard real time, cryptography and secrets, large mutable structures, and programs whose structure is a call stack. For each it says what to do instead, usually a plain function or a request out to the host. It then names the first bucket: interfaces, market data, control, stateful services, incremental computation, simulations, shells and compositors, each a model, a closed set of things that happen, and a plain-data boundary.

The chapter flags its awkward spots inside each dive rather than collecting them, and claims only that the first bucket is most programs and that the tools for it are structurally bad. The hard moments here all end well; the next chapter takes up what happens when a moment cannot end well, which is errors.

## 9. Errors

The chapter opens on the stack trace that ends in a map lookup: a key present a moment ago, `null`, a dereference, a guard added forever. The thesis: a program's own failures are values, and the failures the language cannot make into values do the least damage the transaction allows. The first half is a discipline the type system enforces; the second covers logic errors and broken contracts, such as a cycle that exists only once two widgets are wired together at run time.

The first content section sorts what can fail: missing files, closed sockets, division by zero and out-of-range indexes are cases of a type, and leaving their arm out of a `match` is a compile error. The occurrence then becomes the unit of failure, opened by the half-updated model every reactive system has shown and by Spider's single exception for causality loops. A cycle, overflow or protocol error aborts the occurrence, and the transaction drops its buffered writes. Containment at a construction boundary is the one smaller unit: a `rebuild` whose new generation fails to build does not fire, keeps the tree consistent, and reports through `errors`. Containment to an owning subtree, quarantine, answers the dashboard with one broken panel among twelve: the World passes back the paths it wants quarantined on the next run call.

Static causality and runtime detection come next. A self-relabelling button and a self-feeding mode switch have the same text bind for bind, so the compiler checks cycles inside a widget block and the runtime detects the rest, with construction-abort for cycles found during a rebuild. On whether pure code may panic, the chapter argues against silent wrapping with the `Nat` sum of disk-image sizes that wraps to three kilobytes: overflow aborts, and `Wrap.*` and `Checked.*` give explicit alternatives.

What the program sees of an aborted occurrence is nothing, which is the weakness of the unit and the price of rollback. What the World sees is one `RuntimeError` value with a kind (`Cycle`, `Overflow`, `UnknownPath`, `UnsuppliedState`, `DeferBackwards`, `Component`, `Build`), Prism spans and the occurrence, designed for the moment a differential test fails. Errors inside `Defer` turns stop the turn and the World acts on what committed; component crashes in host code are `Component` errors, never `Unsupported`. Rendered messages are shown, and six worked scenarios follow: a runtime cycle through two widget functions, an overflow in a derived dynamic, a World sending to a vanished path, a state tag with no supplier, deferring backwards, and a `for` key whose block fails to build.

The chapter closes with the invariants collected by party (runtime, World, interceptor, program) and the negative space: no `catch`, no `try`, no runtime retry, no partial commit, no whole-turn rollback, no report naming a runtime node. Each absence is machinery not built. A section appended after the invariants adds causality in types. The error value is the hinge to the next chapter, where transcripts of these reports are what two implementations compare.

## 10. Conformance and testing

The chapter opens on the white-box test that read a private field, broke on a rename, and was fixed by exporting the field. The thesis: a specification only one implementation can check describes that implementation, so the language is tested from the one place two implementations must look identical, the World's side of the boundary. Every test sends plain data to elements and reads plain data back, never naming a node, hold or runtime object.

The Test World is a World with no effects, written once per host language on the world core, that accepts every tag and answers to a script. Everything it sees is printed turn by turn in one canonical transcript form that the harness compares and the differential test diffs. The script language follows: a test written `test name, @w:` with one line per turn (`build`, `idle`, `click`, `send`, `push` or `with` on the line, and `=> expect …` or `=> settles` checks indented under it), element patterns (named fields with `..`, `Ns.*(..)`, `ignore`), and every step (`expect`, `expect_top`, `expect_none`, `expect_top_none`, `expect_count`, `send`, `click`, `with`, `push`, `returns`, `fired`, `quiet`, `requested`, `unrequested`, `errors`), each with a script. Depth inside containers uses the GUI library's `children` field and `ChildInput` convention, and turns define when checks run: always between turns, against committed state.

The law tests give one short program and script per law across events, dynamics, time, widgets, switching, and elements and interception, kept tiny so a failure names a sentence. The integration programs pin meaning as a user meets it: the GUI library in full, the twelve existing programs in a table of what each pins, and nine successors for sentences the twelve do not reach. Each program is also a typed-AST golden and a differential fixture.

The frontend layers follow: the layout corpus of token streams both lexers must match, typed-AST goldens in the text form (the counter's dump given in full) with one file per lexical and expression rule, and negative goldens that fix the exact error message so a worse message is a diff. Below the suite sit the Rust runtime's unit tests with an invariant check after every occurrence, World tests against the core with a fake component, and CLI golden transcripts against a real binary. The differential test is `diff` over `prism dump` and `prism test --transcript` under both implementations.

The chapter closes on the quotable-test rule: every test's name is a sentence from the specification or one that could be added, and a sentence with no test is suspect. Quarantine scripts are Rust-only. The suite fixes what the runtime must produce; the next chapter is the Rust runtime that produces it.

## 11. The Rust runtime

The chapter opens on the list every runtime author knows: a scheduler, dirty tracking, re-entrancy guards, deferred effects, an unsubscribe story with its leaks. The thesis: the Prism runtime needs none of them. It holds events, behaviors and dynamics as nodes with heights, runs one occurrence per call by popping heights in order, commits every hold at the end, and owns the tree of widget nodes that is the program's whole state. A height-ordered action map, a commit list, weak subscriber lists and one synchronous call are the whole engine.

The first half describes `prism_runtime` as it stands on branch `on-fire-repros`, with 38 tests passing and no boundary yet. It covers values (`AnyValue` as a 24-byte enum behind `Value<T>`), the runtime core loop, lazy events that disconnect when unheld, behaviors as the pull half with the only dirty tracking, dynamics where a hold's change event is its input event, widgets with `PolymorphicWidget` so a `rebuild` can rebuild into another kind, and the test backend that reads behaviors directly. The 38 tests are mapped to the laws they pin, and two occurrences are traced through the code.

The target follows: single-threaded on `Rc`/`RefCell`, `send` by `unsafe impl` with the unique-ownership argument and `!Sync`; the run call and its types (`ElementValue`, `TagId`, `Path` of `Bind`, `Gen`, `Key` and `Supplied` segments, `RuntimeError`); the occurrence as a transaction; the graph API with `hold_first` and n-ary maps; `Dynamic::join` as the only join; `!Updated`; the keyed list widget; elements, slots and paths; the element list; routing against the opened list; request collection; state supply by building the supplier widget; and `InterceptWidget`.

The canonical node structure of a lifted application is stated so hand-written and compiled widgets match. Compiled widgets, closures owned through the node's environment (so no collector), and an occurrence traced through the target follow. An invariants section lists what each occurrence promises, and a testing section explains the invariant check. The gap section maps today's code to the target: replacing `Arc`/`Mutex`, adding `Dynamic::join`, elements, paths, interception, and replacing the test backend with the run call.

The chapter flags known issues by name: `trace` leaks, `unreachable!()` stubs, the scheduling edge at `usize::MAX`, the index-0 `DWAction`, `WidgetDelegate` exposing live slots, and unsettable `backend_data`. Performance notes and parallelism (fork-join per height, optimistic occurrences, sharded runtimes) are sketched and left for later, with the promise that none changes the order within an occurrence or a transcript. Three sections appended after them cover values representation, parallel runtimes, and performance and constant factors. The runtime consumes graphs; the next chapter is the compiler that produces the code which builds them.

## 12. The Rust language implementation

The chapter opens on the compiler for a language that runs, whose back half was a fetch-execute loop, and on the reactive framework built over it that became a second runtime fighting the first for control of time. The thesis: a Prism compiler does not emit code that computes. It emits code that, run once, calls the runtime's constructors in order with the right captures, and the resulting graph does the computing. The frontend decides what every line means and writes it into one tree, the typed AST; a lint checks the tree after every pass; a closure compiler walks it once.

The pipeline is laid out and then each stage in order. The lexer and layout pass produce tokens with spans, implement the offside rule, treat inline `:` as a plain token, and keep only a column stack, bracket depth and a whitespace flag. The parser builds a parse tree from a grammar sketch, records spans, and leaves meaning undecided. The resolver handles scopes, qualified names and namespaces, intrinsics, dependency analysis into groups, and placement of placeholders for recursive groups.

Elaboration is the core. The typed AST is defined; Hindley–Milner runs only on the value layer, so time never enters inference; the sigil lattice turns lifting into a lookup on operand sigils; the three traits and literal defaulting are resolved; `for` nodes record whether a block can fire at birth; bindings get build-time and occurrence-time marks; the causality check rejects prompt cycles; exhaustiveness requires catch-alls on open variants; tag-indexed refinement types each `match` arm; `test` items are elaborated. Closure conversion assigns function ids and capture lists, captures through the owning node's environment, and places placeholders and closes. The lint pass re-checks the tree after each conversion, after GHC's core-lint.

The closure compiler produces `IrWidget { program, block, captures, span }` over `Program { functions, blocks, tags, constants }`, with an environment vector, steps that each call one runtime constructor, compiled leaves, a recursion depth guard that reports `Overflow`, boxing at the runtime boundary, spans attached to every node, and the canonical node structure shared with hand-written widgets. The typed-AST text form is specified: one binding per line as `name: sigil type [mark] group = expr @span`, with the counter and the dynamic-of-widgets lift dumped, one definition for printer and parser, and a freeze point. Elements in the compiler cover the tag table, construction, `@Element`, `match` dispatch, `Ns.*`, `Kind`, `intercept` and erasure. Diagnostics and testing (goldens, negative goldens, lint fixtures, round trip, the compiled counter against the hand-written one, and the Haskell differential) follow.

A deep section considers a flat register listing as an alternative lowering and sets it aside until a consumer needs it. The deferred list names optimisation passes, a packed encoding of compiled code, and debug stepping through leaves, each a consumer of the tree that changes nothing in it. Two sections appended after the deferred list cover native backends and incremental compilation. The compiler yields a widget the runtime builds; the next chapter is the host side that drives it.

## 13. Rust Worlds and the world core

The chapter opens on the year the framework's context object became a door everything walked through, until a test could not run without a browser. The thesis: a World is the only part of a Prism system with effects, written in Rust against one synchronous call, and everything a World must get right that is not specific to a screen, terminal or socket is written once in a crate, `prism_world`, so a World is that crate plus a handful of components.

The chapter first lists what the crate refuses to contain, each with its reason, then gives the crate as code: the types, the six-method `Component` trait with each method traced to an obligation, registration and the `World` struct, the turn loop (pushes applied after the first occurrence commits, re-queued on failure, `Defer` occurrences with no new pushes), `DeferTable` keyed by path with generations stripped, snapshot and pushes, slot tracking with discarded late results, `Unsupported`, error reporting, and a harness that drives a runtime from any event loop.

The Test World follows: scripts parsed in `prism_lang`, execution, how `with`, `push`, `requested` and `errors` are implemented, the transcript printer, and what the Test World never touches. The CLI World covers args and environment as state constant after start, standard input as a reader thread started and stopped by its slot, stdout and stderr buffered per turn and flushed at the end, exit as a request acted on after the turn, signal handlers that follow their slot, files through a thread pool and watcher, timers as deadlines in the loop's wait, exit when nothing can cause another occurrence, and the line counter under the real OS. A tokio-based World skeleton shows batching inputs and holding a repeated path for the next turn.

The GUI World section gives the vocabulary, argues for a software rasteriser first, and says how a native-toolkit wrapper differs. The X11-over-sockets World is a Prism library speaking the X11 protocol over a `Net` socket under a World that has only sockets, with a section on what it proves and what it does not. Conformance tests for the core are listed as named Rust tests with a fake component (a `Defer` answered in the next occurrence of the same turn, two `Defer`s making three occurrences, deferring backwards, discarding late results, a slot born in the push occurrence reading the previous snapshot, `Unsupported`, request order, removals before creations, and an aborted occurrence leaving list and snapshot unchanged).

CLI golden transcripts close the chapter, with timers kept out of goldens because wall-clock tests fail on loaded machines, a `ready`-line handshake for signals and watches, and the rule that when the CLI World and the Test World disagree, the CLI World is wrong unless the specification is unclear, in which case the specification gets fixed. The CLI section names some tags as `Cli.Args`, `Cli.Env` and `Cli.Exit`, which the book's vocabulary places under `Process.*`. The next chapter builds the second implementation against the same transcripts.

## 14. The Haskell implementation

The chapter opens on handing a specification to a second person who built something that passed every test and still disagreed on the first untested program, because both had read one sentence differently. The thesis: a specification with one implementation describes that implementation, so the Haskell implementation is a second, independent reading of the language chapters, in the language whose FRP library supplied most of those chapters' semantics. It shares nothing with the Rust side but the typed-AST text form and the transcript format.

The first decision is to interpret, not compile: the typed AST is interpreted at runtime against Reflex, never translated to Haskell source for GHC, so there is no second compiler to be wrong in. The frontend is a separate lexer, parser and elaborator written from the book and the goldens, whose output must match the Rust frontend's text form character for character, with `diff` as its test.

The evaluator is a function from a typed AST and a widget name to a Reflex network, and the chapter goes node kind by node kind. Values are one sum type, since the elaborator already checked types. The monad stack is `PrismM t`, the counterpart of `@A`. The environment, pure expressions, events and dynamics (`current` used only where the typed AST says tag), holds and recursive groups, `dyn` and `@started` (a `dyn` over a constant, never `getPostBuild`), `!Switch` as `switchHold never` and `$Join` as `join`, `for` as `listWithKey` with one `coincidence` over the membership patch only when the can-fire-at-birth flag is set, elements and the list through a writer, `intercept`, state supply, and the run call over `fireEventsAndRead` follow. Errors use rollback by replay on a fresh local timeline, and an occurrence is traced.

"What must not be used" lists the Reflex constructs kept out of a widget block, such as `PostBuildT`, `RequesterT`, `QueryT`, `performEvent` and `liftIO`, so the review is the type checker's. The Test World and transcript printer match the Rust format, a reflex-dom World renders the GUI vocabulary to the DOM, and differential testing diffs dumps and transcripts across implementations. A section weighs what the second reading cannot check and what only it can.

The negative space closes the chapter: no compilation to Haskell, no typed representation of the AST, no forbidden transformers, no effects reachable from a block, no prompt switch or post-build, no transaction inside Spider, and no quarantine, extra Worlds, benchmarks or deployment. Each keeps the implementation small enough to read in a sitting against the chapters it implements. A section appended after them, "The smallest version that pays for itself", orders the first Haskell binary by which law tests it can run. With both implementations described, the next chapter orders the work to build them.

## 15. Plan

The chapter opens on the plan that was a list of features, where the first week went to choosing a starting point because every feature needed a piece of every other. The thesis: cut milestones along the lines the design already has (the run call, the typed AST, the transcript) so each milestone can be handed to a model with the book and the previous code and come back with work judged by named tests and matching transcripts. Eleven milestones run in two tracks that share no code and meet when the compiled counter's transcript matches the hand-written one byte for byte.

Each milestone follows one frame: what it waits on, the work in steps, a done criterion, what it proves, and its risks. Milestone 1 makes the runtime single-threaded and transactional, with `Rc`/`RefCell` first and alone, a re-entry flag reporting `Cycle` instead of a double borrow, and `Dynamic::join`. Milestone 2 adds the boundary: element values, tags, slots, paths as values in tree order and never reused, and the run call, proven by a harness printing the counter's transcript. Milestone 3 adds `InterceptWidget`, state supply and `for`, with the risk that a supplied widget built mid-grandchild must sit under the right parent.

Milestone 4 builds the frontend to the typed AST in a new crate with no runtime dependency, ending with the text form frozen. Milestone 5 is the closure compiler, whose done criterion is the byte-identical counter transcript, with heap cycles through closures as the risk. Milestone 6 is the full conformance suite and script language in `prism_lang`. Milestone 7 is the world core and the CLI World, with performing requests after the turn as the obligation a model is likeliest to break.

Milestones 8 and 9 build the Haskell frontend, with Hindley–Milner choices as its risk, and the Haskell evaluator and Test World, with `listWithKey` consolidation as something to check. Milestone 10 builds GUI Worlds: a software rasteriser, reflex-dom, and the X11-over-sockets proof under the CLI World, judged by golden screenshots and socket transcripts. Milestone 11 completes error reporting with Prism spans. A section on working with a model says what to hand it, what to ask for in four replies, how to check its work (signatures, invariants, tests, then code), what to do when it is stuck (find the sentence and fix the book), and the order to hand milestones out.

"What is not on the plan" names each exclusion and what it buys, so it can be revisited when the price changes. Milestones 10 and 11 describe the GUI vocabulary and error kinds in terms (`Gui.Draw`, `Text.Measure`, `WrongResponseType`, `Panic`) that differ from the book's final vocabulary and need conforming. Everything excluded here is collected in the next chapter. The chapter closes with "Designs that wait on a fact", an index of the appended sections of chapters 3, 7, 9, 11 and 12 with what each must answer.

The chapter opens as four reference tables for a reader who knows the design and wants one page to check against.
