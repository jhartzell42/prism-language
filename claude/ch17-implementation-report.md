# Chapter 17 — A night's implementation: a report

This chapter is a report, not a specification. I am the language model that wrote the rest of this book, and on the night of 11 October 2026 I was asked to build a Prism implementation in Haskell, alone, in a container with no access to Hackage, and to write down what the language was like to implement from its own book. The result is the `claude/prism-hs` directory beside this text: a parser, an evaluator and a Test World for the subset chapter 2 uses, about 3,500 lines, running every program in chapters 2 and 10 and every law in chapter 4 that the prototype's subset reaches, 53 scripts in all. What follows is what building it taught me about the book, in the order the lessons arrived, with the places where I was wrong left in, because a reader who wants to build the next implementation should know which of my complaints survived a second reading.

## What it is and is not

The plan in chapter 14 is to interpret Prism on Reflex. This is not that. The proxy in front of my container admits GitHub and the package registries for Python and Node and nothing else, so `cabal update` and `ghcup` fail before they reach their hosts, and the Haskell available was Ubuntu's GHC 9.4.7 with no `reflex` package. So the evaluator runs on a push graph I wrote in IO, built after Spider's shape: events with heights and one cached firing per occurrence, a scheduler that runs nodes in height order, holds that commit in one batch at the end, `rebuild` and `for` as nodes with heights of their own. It is nearer to a second runtime in Haskell than to chapter 14's interpreter, and that cuts both ways. It is no evidence that Prism's semantics map onto `networkHold`, `switchDyn` and `MonadHold` the way chapter 14 says; I used none of them. It is an independent reading of chapters 2, 4 and 10, and where it agrees with the Rust runtime on a script, the agreement is between two readers of the book and not between Spider and itself.

It has no type checker. Every value is a dynamically typed `Value`, and where the book's checker would decide whether an expression lifts, the prototype guesses: an array literal is plain, a map literal lifts, a `for`'s result kind is read off its last statement. It has no `intercept`, no World but the Test World, no error quarantine, no `update` blocks, no cycle detection: a prompt cycle hangs or reads stale rather than failing. The parser accepts the layout rules of chapter 3 with the colon as block opener, the free and attached sigils, comma-separated application as a postfix on an uppercase head, `then` at the bottom of the precedence table, and the whole of chapter 10's script language.

## Where I was wrong about the book

Three of the findings in my overnight notes did not survive the morning.

The first was construction in the middle of an occurrence. I built from chapters 2 and 10, and chapter 2's rule, that a widget built in n sees all of n, once, told me what had to be true and not how. I got it wrong three ways before three mechanisms made every law pass at once: firings raised during a build are queued until the build is whole, so a block never observes its own half-built state; `rebuild` and `for` are nodes that build their first generation when they first run, in height order, so a rebuild over a dynamic that changed earlier in n builds exactly once, with the new value; and a derived dynamic, a `$Join` or a hold made mid-occurrence over a source that already fired is born holding the new value and does not fire again. Then I read chapter 4, whose section on construction in the middle of an occurrence states the second and third of these under "How an implementation honours it", with the same at-most-once law and the same cache. The lesson is about reading order, not about the book: an implementer who starts from the worked examples will meet this rule as a mystery, and the examples chapter should say that chapter 4 has the mechanism. The one thing chapter 4 did not say, the queue that makes a build whole before anything in it fires, is one sentence, and it is a pull request against this book rather than an edit, like every change this report proposes; the list is at the end.

The second was paths. My notes said chapter 2 used two numbering rules, because the counter prints a `@Button` as `0/#0/0` while the viewer prints `@TextInput`'s parts as `3/0` and `3/1/#0/0`. Chapter 2's convention is one rule, every widget bind takes a position and a widget block numbers its binds under its own; what did not fit it was the library's `@Button`, written out as a widget block around a `rebuild`, which under that rule would print `0/0/#0/0`. The proposed change defines `@Button` and `@Label` as the lifted-element shorthand, one bind and one position, and shows the written-out block as what the shorthand means. The prototype follows the rule as stated and prints chapter 2's listings character for character, the viewer included. My first version numbered a function body's binds in the caller's sequence, which is the wrong rule for a reason the convention now gives: a function's insides should never renumber its caller's slots, and an interceptor routes by path prefix.

The third was double brackets. `((Insert $names, "c", "c") on !add)` lexed in my first lexer as a tuple opening, and I wrote in my notes that `((` was ambiguous and that the double-paren tuple failed the book's own rule against token collisions. Chapter 3's lexical section has the rule that resolves it, and I had implemented half of it: two opens written together are a double bracket only when their matching closes are also written together, and pairing goes outermost first. The lexer now marks each bracket with whether it touches the one before, pairs them, and merges a pair into a double bracket only when both ends touch. Under that rule the line above is two single parentheses, `((a, b))` is a tuple, and `a[b[0]]` ends in two closes. The rule needs pairing, so it is a pass after lexing and not a lexer state, which is what the book says.

## What the book had wrong

Two scripts in chapter 10 wrote `(Insert $keys, Size $keys, unit)`, which under the book's own application rule, a paren-less call takes the rest of its expression and the commas with it, is `Insert $keys, (Size $keys, unit)`. The fix parenthesises `(Size $keys)`. The chapter 10 transcript format had no place for a request fired by a slot that was torn down in the same occurrence, which the chat program does when it sends and changes address at once; the World still has to perform that send, so the proposed format prints such slots under `torn down:`. The script language could address a slot only by pattern, so two rows with identical buttons could not be clicked individually, and every list test had to change a row before adding a second; `click at path` and `send at path` are the proposed forms. And chapter 8 assumed a prelude of plain functions the book never listed; the list the prototype needed to run every program is proposed for appendix C.

## What just worked

More than I expected. `then` as the hold keyword parsed cleanly at the bottom of the precedence table, and `on` and `|` inside an application's last argument gave no trouble once application was a postfix on an applicable head rather than a form at the top of an expression, which was my one real parser bug: `@ !Switch !!clicks` had split into `@ !Switch` and a new statement. Names keyed by sigil and base let `!motd` and `$motd` coexist with the pronoun `_` resolving across sigils, after a first version keyed by base alone showed an event where a label wanted text. Tuple-pattern binds, `((!rx, $link)) <- @Element Net.Socket(..)`, an element with both `responds` and `state` returning the pair, worked once patterns took commas. A `$` name read through a tag by the `requests` expression of the very element that defines it, the chat program's socket, needed a forward dynamic, a placeholder connected when the real one is bound, which is what `RecursiveDo` would have given for free; so did top-level recursion, which needed every definition to be a thunk over the final environment before a function could call itself. Holds are pre-created in a pass before the block's other statements, with a forward change event, so a hold can be used above its line; the limit is that a hold's initial value cannot mention a later block-local binding, which chapter 3's binding groups handle and the pre-pass does not.

The equality rule showed itself exactly as chapter 2's listing shows it: a row's dynamic fires on every change to the map, so every row's label rebuilds on every add, and the prototype's generation numbers match the book's. That is the performance item chapter 11 names, confirmed by a second implementation agreeing with the first about a cost neither wanted.

## What I would tell the next implementer

Read chapter 4 before chapter 2. Build the Test World first, because the script language is the specification you can run, and chapter 10's scripts ran as written except where the book was wrong. Expect the type checker to be a design job before it is a coding job: half the lifting decisions in chapter 3 are stated by example, and the places where a dynamically typed prototype guesses are exactly the places a checker decides, so a test suite written against this prototype is conditional on those guesses until a checker exists. Treat the prompt-cycle check as a prerequisite for any error test, not a refinement. And write the Reflex interpreter chapter 14 describes, on a machine that can reach Hackage; the parser, the Test World and the scripts carry over unchanged, and only the evaluator and the graph are replaced, which is the experiment this report could not run.

As for what it was like: the graph was a morning, and the one sentence in chapter 2 was the night. Everything else in the book is a law you can test against. The thing I missed most without Reflex was not a primitive but a second opinion, since when my viewer printed a path the book did not, the only way to know which of us was wrong was to read the book again, and the second reading was usually right.
